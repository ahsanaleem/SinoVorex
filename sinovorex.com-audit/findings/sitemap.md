## Findings

### Finding 1 — `lastmod` does not reflect real content changes (Medium)
**Evidence:** `app/sitemap.ts` line 6 and 8–11:
```ts
const now = new Date();
return [
  { url: `${SITE_URL}/`, lastModified: now, ... },
  ...SERVICES.map((s) => ({ url: ..., lastModified: now, ... })),
  { url: `${SITE_URL}/privacy`, lastModified: now, ... },
  { url: `${SITE_URL}/terms`, lastModified: now, ... },
];
```
Live sitemap shows **all 9 URLs sharing the identical timestamp** `2026-10-18T10:01:02.002Z`. On re-fetch a day later (2026-10-19) the value had not changed, confirming this is the timestamp of the last time the Vercel edge cache regenerated the route (`Cache-Control: public, max-age=0, must-revalidate`, `X-Vercel-Cache: HIT`), not a per-page content-change date. Every subsequent cache regeneration will stamp every URL with that one new "now" value regardless of whether any page's content actually changed — i.e., `lastmod` carries no real signal and will churn on every rebuild/redeploy.

**Why it matters:** Google explicitly says `lastmod` is only useful (and trusted) when it reflects the real last significant modification date; identical, auto-"now" timestamps across all URLs is a known anti-pattern that causes Google to distrust/ignore the field entirely.

**Recommendation (code fix for `app/sitemap.ts`):** Use real per-page dates instead of a single `new Date()` call. Two concrete options:

Option A — static, hand-maintained per-page dates (simplest, matches a low-page-count marketing site):
```ts
import type { MetadataRoute } from "next";
import { SERVICES } from "@/components/sinovorex/data";
import { SITE_URL } from "@/lib/site";

// Update each date only when that page's content materially changes.
const LAST_MODIFIED = {
  home: new Date("2026-10-01"),
  services: new Date("2026-10-01"),
  privacy: new Date("2026-09-15"),
  terms: new Date("2026-09-15"),
};

export default function sitemap(): MetadataRoute.Sitemap {
  return [
    { url: `${SITE_URL}/`, lastModified: LAST_MODIFIED.home, changeFrequency: "monthly", priority: 1 },
    ...SERVICES.map((s) => ({
      url: `${SITE_URL}/services/${s.slug}`,
      lastModified: LAST_MODIFIED.services,
      changeFrequency: "monthly" as const,
      priority: 0.8,
    })),
    { url: `${SITE_URL}/privacy`, lastModified: LAST_MODIFIED.privacy, changeFrequency: "yearly", priority: 0.2 },
    { url: `${SITE_URL}/terms`, lastModified: LAST_MODIFIED.terms, changeFrequency: "yearly", priority: 0.2 },
  ];
}
```

Option B — derive from git history at build time (stays accurate automatically as files change), e.g. using `child_process.execSync('git log -1 --format=%cI -- <file>')` per route file, cached at build time. Only worth the complexity if the team won't reliably update Option A's hardcoded dates.

Either way, stop calling `new Date()`/`Date.now()` inside `sitemap.ts`.

### Finding 2 — Deprecated `priority`/`changefreq` tags present (Info)
**Evidence:** Every `<url>` entry in the live sitemap includes `<changefreq>` and `<priority>` (e.g. `<priority>1</priority>`, `<priority>0.8</priority>`, `<priority>0.2</priority>`), generated by the `priority`/`changeFrequency` fields in `app/sitemap.ts`.

**Why it matters:** Google has confirmed both fields are ignored for ranking/crawl-prioritization purposes. They are harmless but add unnecessary bytes/noise.

**Recommendation:** Optional cleanup — remove `changeFrequency` and `priority` from every entry in `app/sitemap.ts`, leaving only `url` and `lastModified`:
```ts
export default function sitemap(): MetadataRoute.Sitemap {
  return [
    { url: `${SITE_URL}/`, lastModified: LAST_MODIFIED.home },
    ...SERVICES.map((s) => ({ url: `${SITE_URL}/services/${s.slug}`, lastModified: LAST_MODIFIED.services })),
    { url: `${SITE_URL}/privacy`, lastModified: LAST_MODIFIED.privacy },
    { url: `${SITE_URL}/terms`, lastModified: LAST_MODIFIED.terms },
  ];
}
```
Not required — leaving them in is not an error, just dead weight.

### Finding 3 — `www.sinovorex.com` has no valid TLS/DNS setup (Info / out-of-scope for sitemap correctness)
**Evidence:** `curl https://www.sinovorex.com/` fails with `schannel: failed to receive handshake, SSL/TLS connection failed` (no working cert/listener on the `www` host), while the bare domain `https://sinovorex.com/` works and `http://sinovorex.com/` correctly 308-redirects to it.

**Why it matters:** This does not affect the sitemap itself (the sitemap correctly only ever references the bare `https://sinovorex.com` host, matching `SITE_URL` and the canonical tags, so there is no self-inconsistency). It's flagged only because if anyone or any external link ever points at `www.sinovorex.com`, it currently hard-fails rather than redirecting to the canonical host. Not a sitemap defect — no code change needed in `app/sitemap.ts`/`app/robots.ts`; mentioned for completeness since canonical-host consistency was in scope.

**Recommendation:** Outside this agent's remit (infra/DNS/Vercel domain config, not `sitemap.ts`/`robots.ts`). If `www` is intended to be unused, no action needed as long as it isn't linked anywhere; otherwise add a `www` → apex redirect at the DNS/CDN level.
